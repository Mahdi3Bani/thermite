# Changelog

Each release of Thermite, newest first. Versions 0.x make no upgrade promise: read [Known limits](docs/_site/src/content/docs/reference/known-limits.md) before you upgrade.

## [Unreleased]: v0.1.0, the first public release

### Install and run

- A rig whose broker stops at start with a fatal error holds it a minute before it exits (`THERMITE_FATAL_HOLD_SECONDS`, 60 in the one-container rig image), so the pod's log on RunPod keeps the error and the container does not restart every few seconds. A throw while the rig's folders are prepared is logged as fatal too.
- The images are built on Node.js 22.23.4. A release builds every image layer again, without the build cache, so each image has its base's newest system packages.
- Install from published images, with no build. Each release attaches a compose file that pins the images by digest, and `thermite local init` makes the stack's secret files. Building from source stays for contributors.
- The images:
  - control, the CPU harness and the supervisor, for amd64 and arm64;
  - the CUDA harness, and the one-container rig image for RunPod built on it, for amd64. The release's compose file gives control the rig image, so a launch on RunPod needs no image.
- Control's image carries kubectl, for rigs on Kubernetes clusters, with its license (Apache-2.0) as a file. The image's license label stays `MIT`.
- `thermite doctor` checks the machine. It covers the container engine, the compose tool, ports, disk, the clock, the GPU toolkit, and whether control and the model can be reached, and it says how to fix each problem.
- Control and every rig report their versions. Control marks a rig that is behind it, refuses a rig it cannot work with, and shows a rig that stopped reporting as stale or offline.

### Rigs

- Rigs on your own machines over SSH, and on Kubernetes clusters, in a namespace that control creates or in a slot that your operators made.
- Rigs on RunPod GPUs, on Secure cloud, launched by the owner from the dashboard's **Launch on RunPod** or over REST, MCP or the command line:
  - control connects to the pod through RunPod's proxy, and enrolls it with a one-time code;
  - the pod runs one container that holds the harness and the supervisor;
  - control tracks each rig's hourly price and spend, and applies a spend limit or an idle stop only when you set one. The dashboard's launch form fills in an idle stop of 30 minutes, which you can change or clear, and a new run wakes a pod its idle stop stopped;
  - stop, start, restart, full reset and terminate, where terminate waits until every result has left the pod.
  - the rig works on the pod's own disk, which RunPod empties at a stop, and keeps a snapshot of its state on the pod's volume, which refuses even root a change of owner. Root takes it every 5 minutes, after each export, after enrollment and at a stop: the ledger with SQLite's backup, only what changed, each new one swapped in by rename once it is whole. A start on an empty disk restores the newest, plain files and folders only, with the owners and modes the rig's parts need, so the pod reports again with its keys, enrollment and token. Settings: `THERMITE_STATE_SNAPSHOT_DIR`, `THERMITE_STATE_SNAPSHOT_MINUTES` and `THERMITE_STATE_SNAPSHOT_STOP_SECONDS`.
  - RunPod's volume ignores file modes, so every user in the pod could read the snapshot: it is sealed. Control makes a new key for each pod at its launch (`THERMITE_STATE_SNAPSHOT_KEY`, a launch value it keeps no copy of), which only root holds in the pod. Every file is encrypted and authenticated with AES-256-GCM and named by a keyed hash of its content, and the manifest, which binds every file, is sealed too. A start restores a snapshot only when its manifest and every file verify, and otherwise refuses it whole, logs `the snapshot did not verify: <why>` and starts empty. A pod launched without the key takes and restores no snapshot. The isolation check passes an open snapshot folder that holds only sealed files ("open, sealed"), fails on any file that is not sealed, and looks for the key in every environment it can read (`state-snapshot`, `snapshot-key`).
  - a RunPod rig's page shows its pod log, **Pod log**, read from RunPod's API with the cloud's key in **Providers**: the newest lines from the container and from RunPod's host, each marked, with **Read again**. Before the rig's first report it sits under **Getting it ready** and is read once as the page opens: it says why a pod runs but never enrolls, with no RunPod console. Over REST, `GET /v1/rigs/<rig>/runpod/logs` (the owner's token), and over MCP, `runpod_rig_logs` (the owner's and the operator's). Control stops a read after 2 seconds with no new line or 10 seconds in all, and takes what looks like a key or token out of each line.
- The Rigs list is a table: each rig's state, where it runs, its version, the run at work and, on RunPod, its price.
- Edit rig works without the browser: besides each agent's model, a rig's parts on or off, workers at a time, a trial's length and turns, its promotion rule and its GPU split change with `POST /v1/rigs/<rig>/settings` and the MCP tool `set_rig_settings`, and read with `GET /v1/rigs/<rig>/settings` and `rig_settings`. They send only what differs from what the rig reports and refuse in the page's words. An operator's token changes all but the promotion rule and the GPU split.
- A rig takes model files by URL and checksum, with progress. It sends its exports to control when the project has no results repository.

### Campaigns

- Three campaign modes: hill climb, goal and research.
- The New campaign page and Start a run. Start a run also works without the browser: `POST /v1/campaigns/<campaign>/runs`, the MCP tool `start_run` and `thermite run start` take the same fields and give the same refusals. A campaign's project can be a folder inside a repository. A sample project and its kit are in `examples/matmul-cpu`.
- Campaigns, runs and Live per run, built for scanning. The owner messages the agents and the advisors from one message box, and sees who read each message.
- Give control a kit repository written elsewhere, as a git bundle: `thermite kit add`, `POST /v1/kits/<name>` (the owner's token, up to 64 MiB) or the MCP tool `kit_add` (the owner's and an operator's, up to 3,000,000 bytes of bundle). Control checks the bundle, keeps every commit with its id, and makes the kit's head the bundle's `HEAD`, its only branch or the ref given, which needs a valid `kit.json`. A head moves only forward unless forced, and a forced one keeps the old head's commits. Rigs fetch the kit from control by commit, as they fetch the kits New campaign writes: `{"control": "kits/<name>"}` as the import's source, or `thermite assign --kit control:NAME`. `thermite kit list`, `GET /v1/kits` and the MCP tool `kits` list them; each kit taken is in the audit log as `kit_added`.
- Copy a campaign under a new name, with the same contract and kit and its own empty folder, to compare two models from zero: **Copy** on the campaign's page, `POST /v1/campaigns/<campaign>/copy`, the MCP tool `copy_campaign` and `thermite campaign copy`. The page's panel checks the copy's name as you type and opens the copy's page, which says where it came from. A research campaign's copy can name other MCP servers for its agents, such as a web search service.
- A campaign's brief, for every mode, on its own step of New campaign, **2 The brief**, after **1 Aim**: **Additional information** in Markdown with no length limit, with its preview beside it as you type, **Starting links**, one address per line, and **Hypotheses**, one per box. Hill climb and goal add **Ideas to try**; a research campaign's topic and questions are there too, each question in its own box, as long as it needs. A research campaign's starting links are its seeds, which the harness now fetches and archives when the run starts; its step 4 is **Time and tools**. The contract keeps the brief as `notes`, `links` (hill climb and goal), `ideas` and `hypotheses`, so old contracts keep their hashes. The planner gets it whole, and the advisors ahead of the evidence and the diff; each worker's brief has it whole up to 32,000 characters, and the run's folder keeps it whole as `BRIEF.md`. A research run starts with the hypotheses as its own. The campaign's page shows it, Copy keeps it, and `thermite assign` and a copy over REST, MCP or the command line take it.
- Archive a campaign, and sort campaigns into folders in the dashboard's left navigation. **Archive**, under **⋯** on a campaign's page, takes it out of the navigation, **Needs you** and the Overview's lists; its runs, results and kits stay. Control refuses it, in words, while a run of it is at work or waits to start, and starts or resumes no run of an archived campaign. **Campaigns › Archived** lists them, with **Unarchive**. An archived campaign keeps its folder, which neither shows nor counts it, and **Unarchive** brings it back into that folder; a folder that holds archived campaigns is not deleted. The folder button beside **Campaigns** in the navigation makes a folder; each folder's **⋯** renames it, or deletes it when it is empty. Drag a campaign onto a folder, or use **Move to folder** on its page. A folder folds, and the browser remembers it. Over REST (`POST /v1/campaigns/<campaign>/archive`, `/unarchive` and `/folder`, and `/v1/campaign-folders`) and MCP (`archive_campaign`, `unarchive_campaign`, `campaign_folders`, `create_campaign_folder`, `rename_campaign_folder`, `delete_campaign_folder` and `move_campaign`), each change in the audit log.
- The left navigation lists every campaign that is not archived, finished ones too, and no longer lists the rigs: the **Rigs** page does.
- One experiment queue for each run. The planner coordinates it. The owner, the advisors and the lanes add to it, and `thermite assign --queue-from` copies another run's untried experiments.
- The queue stays full of ideas:
  - **The teachers put ideas first.** Each round's main product is a portfolio of new opportunities, as many as are distinct and evidenced, each with its mechanism, gain bound, smallest experiment and matched control, stop condition, why it is new and its evidence; each one becomes an experiment in the queue. Rules come second, only when new evidence calls for one. The merged by model drops no distinct idea, and code adds back any it leaves out.
  - **Code refuses a rule that freezes the queue's size or pins an experiment,** such as "do not add queue entries" or "retry x-… first", in the supervisor and the rig, and says why in Live and History. Such a rule of the teachers', set before, no longer reaches the planner. Only clear words are refused: a rule about a direction or a kind of idea ("do not add more unrolling experiments"), about a project's own queues ("back off when the submission queue is full"), or that cites an experiment as evidence stands.
  - **The teachers read the run's code and evidence,** read only: the champion's tree, each attempt's diff and the judge's public reasons, and why each experiment tried ended as it did. Held-out results and the kit stay out. A research run has no code, so its teachers get none of these tools; the harness refuses a code read of a research run in words, and a read of a repository that is not on the rig says so, never `spawn git ENOENT`.
  - **The teachers read what the run itself found,** read only: its sources with their archived text, its claims with the harness's reasons for each draft, its hypotheses, findings and notes, the report and each lane's files, a page at a time or by a search of words (`list_research`, `read_source`, `read_research_file`, `search_research`). A research run's brief starts with a short summary: the counts, each question's coverage and the start of the newest report. The teachers are told to read what the run found before they propose. A hill-climb or goal run's teachers get the same once its workers recorded a source, a claim or a note. Teachers that may fetch any web page get none of these tools, and Live says so once.
  - **Ideas kept ready:** a campaign's target queue depth (`lanes.queue_target`), two for each lane by default, set on the New campaign page and shown on the campaign's page. A target, not a cap. Below it, the planner is asked to top the queue up, the lanes' distinct ideas go up next, and the teachers are asked for ideas at once.
  - **Lanes propose follow-ups.** A worker's brief asks it to propose each distinct follow-up before it submits or stops.
- `thermite assign --note` and `thermite assign-payload --note` keep a text with the run, shown as `Note: …` on the run's page in the knowledge base. `--direction`, the flag's old name, still works in v0.1.0 and says on standard error that it is now `--note`: a direction is now a named line of experiments. The signed command keeps the field's name, `direction`.
- Rules for the planner name the run's directions. The owner writes them in plain words on the run's **Planner** tab, under **Tell the planner**, where `:` picks one of the run's directions, and the planner makes the rules at its next round. An old rule in words, from before rules named directions, is converted to a rule on a named direction at the planner's next round: it keeps its kind, author and why, shows `converted from:` and the old words, and is never dropped without a rule in its place.
- Agents run in Pi, OpenCode v2, Claude Code or the Codex CLI, chosen for each rig. The harness images carry OpenCode and the Codex CLI, each with its license. Claude Code runs under the rig's own isolation, as the other harnesses do, with its own sandbox off, and gets its sign-in on a file descriptor, never in an environment or a file. An advisor on a Claude subscription runs Claude Code the same way, with none of Claude Code's own tools, so the images carry no bubblewrap.
- Each kind of agent can have its own model and effort: the workers, the planner, the teachers, the auditor and the review panel, on Edit rig and over REST and MCP (`set_rig_model` with `agent`, and `rig_models` to read them). Each agent's model can take a cap on its context window, to compare two models at the same window, and its own compaction point.
- One name for each agent, on the screens, the pages, the API, MCP and the events, in two groups. The work: the workers and the planner. The advisors: the teachers, the auditor and the review panel. The teachers take one or two models; with two, a merged by model joins their advice into one set (`set_rig_model`'s `second_model` and `merged_by`, and `rig_models`' `teachers: {models, merged_by}`). One teacher works with no merge. An advisor with no model of its own uses the rig default, its advisors file, whose fields are now `merged_by` and `review_panel`. The old names `combiner` and `panel` are still taken in v0.1.0, by the API, MCP and the advisors file, and the answer says what each is now. A check of the pages refuses the old names.
- Edit rig's agents come in two groups, The work and The advisors, each agent with its job on one line. Every line has its own **Model**, **Effort**, **Runs in** and **Context**: the context window and the compaction point, changed in a small panel under the cell. **+ second teacher** adds a second teacher and a **merged by** line. The page checks each line as you type, in control's words, and says each change in a short sentence; control saves nothing when a line is refused. The form works without the page's script.
- A line on Edit rig with no model names what its agent uses then, not "rig default". An advisor's first **Model** choice names the model of the rig's advisors file, such as `rig's file: opus-5.5`, with the file's program and window greyed under **Runs in** and **Context**; it says `none: off` when the file has none, and `rig's file` until the supervisor has reported. The workers' says `rig's settings: <model>`, or `none: can't run`, and **Effort**'s empty choice is `model's default`. The supervisor reports what its advisors file sets up for each role: model, program, provider name and kind, window and point, never a key, a token, an address or a path. `rig_models` and `GET /v1/rigs/<rig>/model` give it as `advisors_file`.
- Each kind of agent also runs in the program of the owner's choice, on Edit rig and over REST and MCP (`set_rig_model`'s `harness`, for any `agent`): Pi, OpenCode v2, Claude Code or the Codex CLI. A model that a program can't run is refused in words. A planner with its own model plans in its own program, and reaches its own provider through the harness's proxy. An advisor in OpenCode or Codex runs in the supervisor in a folder of its own, with none of the program's own tools: only the search of the run's past research and the kit's MCP tools, and the model through a proxy for the call that adds the key. The supervisor image now carries OpenCode and the Codex CLI with their licenses, and its license label is `MIT AND Apache-2.0`.
- A conversation that grows never ends a trial, and no agent is told to submit early because of it. Near the model's context window (by default 80% of it; `compact_at`, from 50 to 95, sets the share with each agent's model over REST and MCP) the conversation is compacted and the agent goes on. In Pi, the harness first keeps the whole conversation in the run's research folder (`compactions/`), where the agent can read it and the run keeps it, then asks the same model for a summary that names it. OpenCode v2, Codex and Claude Code compact on their own, with the window and the point Thermite sets in their settings, and their conversation is kept there too, with a summary that names it: Claude Code's PreCompact hook copies its transcript and adds the line to the compaction's instructions; Codex's compaction prompt is Thermite's own, and Thermite reads Codex's record of the thread; Thermite's OpenCode plugin keeps the session in OpenCode's compaction hook, adds the line, and says when each compaction ends. Each compaction is a `context_compacted` event, in History and Live, with the summary.
- The advisors compact too. An advisor's call in Pi compacts as the planner's does, and the supervisor keeps the conversation with its records of the round, never where the run's workers read; an advisor in Claude Code, OpenCode or Codex gets the window and the point in that program's settings, and the supervisor keeps its conversation the same way. An advisor's package (a brief, an audit's or a review's) is cut to fit its window, and its input says so.
- A campaign can set its own context window and compaction point for all its runs' agents: the contract's optional `agents_context`, set with `POST /v1/campaigns/<campaign>/context`, the MCP tool `set_campaign_context`, `thermite campaign context`, a copy's `agents_context` (`copy_campaign`, `thermite campaign copy --context-window --compact-at`) or `thermite assign --context-window --compact-at`. Each agent's window is the lower of the campaign's and its own. Start a run says what applies to each agent, and refuses a window above what a provider lists for one of the rig's agents' models. On the dashboard, **Agents' context** sets it on the campaign's page, with what applies on each rig, in New campaign's step 4 and in the Copy panel; Start a run's panel says what the chosen rig's workers get, and keeps **Start the run** off on a rig where a run would be refused.
- On a CUDA rig, the agents find CUDA's tools by name in every harness.
- A claim's quote names its source by the id `fetch` returned, or by the address or the research folder's file name of exactly one archived source. The quote is then checked against that source word for word, as by its id, and the claim keeps what the worker cited. Any other source is a problem that says what it could be: `fetch it first`, the ids an address was archived as, or an archived address written another way. A number from a heading of the claim, such as `Question 0:`, is still refused, and its problem says to give the question's number in `question`. The `claim_added` event carries the quotes' sources and a draft's problems, and the run's **History** shows each claim, with a draft's reasons.
- Field notes from the workers, the planner and the advisors. Thermite keeps its own knowledge base, with a folder for each campaign, and the owner grants which campaigns may read which folders. Workers, the planner and the advisors can search what they may read.
- Each goal's real check, under **How it is checked**: in a run's **Goals** block, on a campaign's page, and on the page of a campaign saved with no run yet. It shows the kit's verifier or the metric threshold, the cases it runs on with the parameters the kit runs each with, each case's time limit, and the held-out cases by name only, so a contract's goal text that drifted from the kit shows. A goal run's rig reports it when the run starts (the `goal_checks` event, and `goal_checks` in `get_run` and `GET /v1/rigs/<rig>/view`); control also reads it from a kit it keeps, and says when it can read neither.
- A confirmation that fails on a held-out case says how, safely. The judge records each held-out case's name and its kind of failure, from a closed list (`threshold_missed`, `timed_out`, `crashed`, `check_failed`, `non_finite`, `no_cell`), and the measured value against its threshold where the check gives one: a threshold goal's mean and interval, a hill climb's ratio to the champion. The owner sees them on the attempt's page under **Held-out checks**, in **History**, in `get_run` and `GET /v1/rigs/<rig>/view`, and in the judge's new `held_out_checked` event. The agents see only that a held-out check failed and its kind, such as `confirmation failed: a held-out check timed out`: in the verdict's reasons, the planner's and the teachers' evidence and a worker's `status`. No one gets a held-out case's inputs, its output or the check's words. A hill climb's failed confirmation now shows the measured cases' figures, where it showed none before. A hill climb's contract that names a cell in both `cells` and `held_out_cells` is refused in words: the cell would be measured at screening. Control's agent token reads held-out checks as the agents do: in `get_run` and `recent_events`, their kinds and words, with no case, value, threshold or time limit, and a goal's checks without its held-out cases. An error in the judge's own work while held-out cases run reaches the agents only as `a held-out check could not finish (an infrastructure failure)`; the rig's log keeps it. A run's start refuses a kit whose case, among those the contract runs, lacks a rate metric's `work` parameter above zero, and New campaign scores a rate only when every case, hidden ones too, has its **Work done**.
- A threshold goal whose cells mix measured and held-out cases is screened on its measured cases; before, it could never be met, for lack of a value from the held-out ones.
- A goal report keeps what it measured. A goal checked by a kit verifier, met or not, gives each measured case's metrics, as a threshold goal gives its mean and range: in its reasons (`verifier quality passed on wiki: wiki: ppl_ratio 1.00213`), as `values` in the `goal_report` event, `get_run` and `GET /v1/rigs/<rig>/view`, and under each goal in the run's **Goals** block, which now shows a met goal's line too. A case whose output the check refused gives the numbers its check reported. The planner and each worker's brief read them; a held-out case's values are kept nowhere.
- While the judge checks a second time a champion that met every required goal, a goal run starts no new round or trial: a trial at work goes on, the run's page and **Live** say why, and the lanes go on if the check does not agree or fails (`goals_confirming` in `get_run`). A second check queued for an earlier champion now counts as the first check of the new one, so a run never closes on one check.
- The owner closes a run by hand, for good: **Close run**, under **⋯** on a running or paused run's page, with a reason and the words `close <run>` typed to confirm, and `close_run {run, reason}` over REST, `thermite command` and MCP with the owner's token (not the operator's or an agent's). The run closes as a run that met its goals does, with the owner's reason: its trials stop, nothing new starts, its jobs waiting for the judge never run, a research run gets its final report, and its results stay and reach the next export. A closed run can't be resumed or paused again, and closing it twice is refused in words. A job the judge was measuring when a run closed no longer replaces the owner's reason with its own.
- Nothing waits for the owner in a closed run, however it closed. A change waiting for approval or an audit, a review the review panel passed and a "not possible" proposal leave **Needs you** and every count of it: the sidebar, the status bar, the Campaigns page and the run's own pages. The rig refuses `approve_promotion`, `decline_promotion`, `accept_review` and `conclude` for a closed run in words, such as `run <run> is closed: none of its changes can become the champion`, the auditor gets none of its audits, and none of its changes becomes the champion by a decision. Such a change reads **Run closed**, and its page says why, with no buttons. A closed run's `pending_promotions` is empty over REST and MCP.
- Before a goal run closes, its champion's second check also runs the held-out cases of every goal it meets; before, an attempt's confirmation ran them only for the goals it newly met, so a goal met long before never ran them. The run closes only if each passes. When one fails, the goal is not met again (`unmet`, `not confirmed: <kinds>; on the measured cells: …`), the report has `complete: false` and `not_confirmed`, and the lanes go on: the planner and the workers read which goal and its kinds of failure, never which case. The owner sees each case and its kind under the run's goals (**Held-out checks of champion #n**), in **History**, as `champion_held_out` in `get_run` and `GET /v1/rigs/<rig>/view`, and in a `held_out_checked` event on the run with `champion_seq`. The rig's `held_out` table keeps a champion's record by run and champion, with no attempt (ledger schema version 20).
- A change the static checks refuse says why everywhere it is looked at, not only to the trial that submitted it: its event `attempt_recorded` (the first 20 violations), the attempt's page under **Refused before building**, the run's **History**, `get_run` and `GET /v1/rigs/<rig>/view`, the knowledge base's attempt item, and the planner's and the teachers' evidence (the first 5). A worker's `status` of an attempt now answers for any attempt of its campaign on the rig, such as another lane's or an earlier run's, with every violation; before, it answered 404 for any attempt but its own lane's in the same run.
- A kit's cell can set its own time limit: `{"params": {…}, "timeout_s": 1800}` in `cells` replaces `run.timeout_s` for that cell's runs only, so one slow cell no longer sets the limit for all of them. A cell of parameters alone keeps `run.timeout_s`, so older kits work as they are. Every time limit in a kit, the cells', the build's, the run's and the check's, is at most 86400 seconds (a day), the longest the judge runs anything; the kit check refuses a longer one in words, where before such a kit's runs waited for ever. A request the judge's broker refuses is answered under its own id, so the call that sent it fails at once.
- MCP servers for the agents. The owner adds a server once in Settings, with an OAuth sign-in, a key, a client ID and secret, or none; control seals the secret and reads the server's tools. A campaign's kit names its servers, the agents that get each, and, when narrowed, their tools. Workers and the planner call them through the rig's harness, the advisors through its supervisor; no agent sees a secret, and a server that fails does not stop a run. Rigs on RunPod get their servers through control's connection to the pod. A run's first plan and trial wait up to 2 minutes for the rig to hold the servers its kit gives the workers and the planner, so a trial no longer starts just before control hands them over and works its whole length without them; a server still missing then, or one control says it can't give, is named in Live and History (`mcp_servers_wait`), and the run goes on without it.

- The model provider decides when agents can work. A provider's error is sorted by its kind: a rate limit waits for the time the provider gives (`Retry-After`, its reset headers or its words) and goes on in the same conversation; a 5xx or a broken connection waits a growing pause and goes on; no credits, a refused key or a model the provider does not serve on the key stops the run's agents and shows the run in **Needs you** (**Agents stopped**) with the provider's words. A 5xx or a refused request that never clears, with no model call that worked for 30 minutes, stops them the same way (`no model call worked for 30 minutes`): pacing, so that it shows, not a cap; when a check passes, the lane whose trial ended starts afresh. A 429 in a quota's words is a rate limit when it says `RESOURCE_EXHAUSTED` or gives a time to try again; OpenAI's `insufficient_quota` and a 402 are no credits. Only the provider's own answers are sorted: a local failure, such as a workspace that could not be set up or a program that exited, never stops the agents, whatever its words. No trial or plan starts while the workers' model check fails. The model is checked again after a minute, then less often, and at once with **Check the model now**; a passing check or another model ends the stop. A research run's clock stops while its agents cannot run. Pi, OpenCode v2, Claude Code and Codex answer alike; the harness's model proxy tells the kind from the provider's answer.
- A model call whose stream goes silent no longer holds a trial forever. When the provider sends no data for 600 s (`THERMITE_MODEL_STALL_SECONDS`; `0` turns it off), while the call waits for its answer or for the answer's next part, the call is broken off as the provider's passing fault: the trial waits and goes on in the same conversation, and **Live** says `the model's stream went silent for 600 s: retried …`. Keep-alive comment lines and pings are not data, so a gateway that keeps the connection open while its model sends nothing is caught too. It covers every Pi call (workers, research workers, the planner, compactions, model checks and the advisors) and the model proxy's calls for OpenCode and Codex, which get a 504 or a broken connection. It detects silence, not a cap: a call that keeps sending data is never cut. Silent calls that keep coming stop the run's agents after 30 minutes, as other passing faults do.
- No hidden limits on a trial: no trial length (it was 20 minutes), no 8,192-token reply cap (a route carries the model's maximum output from the provider's list, else none is sent; Anthropic's API gets 32,000), no 6-failures or 5-cut-offs rule, no 30-minute cool-down, no fixed number of nudges (a worker is told to go on while it keeps working), no time limit on a planner call (it was 180 s, or 300 s), no 3-hour cap on a round, and no 10-minute limit on a dev run's wait. The advisors' calls from control have no turn, time or reply limit either (24 turns, 900 s, 8,192 tokens). Each is now a setting with no default: the contract's `lanes.limits.trial_minutes`, `failures_in_a_row`, `cutoffs_in_a_row` and `nudges`; Edit rig's **One trial lasts (minutes)** and `THERMITE_TRIAL_MINUTES`; the advisors file's `max_tokens`, `max_turns` and `timeout_s`. A rig's settings file from before keeps no 20-minute trial: it was the old default. A research run with no `max_duration` runs until someone stops it: `min_duration` is a floor, never a stop.
- **Update to these images** and `update_rig_images` drain a rig at work first: it starts no new trial, plan or judge job, and its pods restart once its running trials and the judge's job under way end. A plan that ends during the drain records its round and starts no trial; a judge job whose lease ran out is not waited for, and is taken back to the queue while draining. The rig's page shows what it waits for, with **Update now, without waiting** and **Call the update off**; `update_rig_images` takes `wait: false`. A stop of the harness records its running trials as interrupted, with their workers' counters. Each lane's build cache now survives a restart: the harness's start keeps it while it empties the rest of `/scratch`.
- An experiment whose trial never really tried it (interrupted by a pause, a reset or a restart before it submitted, or ended on the provider's error) goes back to the top of the queue as the same experiment, with how many times and why (`experiment_returned`), not as a copy. A trial stopped after it submitted keeps its experiment done with that change, even when its worker could not report it. Every tried experiment keeps how its trial ended in words, which the planner's and the teachers' briefs show beside its result. A trial interrupted by a restart keeps the turns and tokens its worker last reported.
- The planner's tool schema and prompt state every limit its answer is held to, and a focus may be 4,000 characters. Each try that gives no plan is recorded with its real cause in the round's `epoch_started` (`causes`) and in **History**: timeout, text only, cut off, the provider's error, cancelled, or refused with which rules. A research run's rounds count as research rounds, never as planner fallbacks. The fallback plan skips a direction whose goals the champion already meets.
- Hands-off by default: a win the judge confirms becomes the champion with no step of the owner's, in every mode. When the campaign calls for an audit and the rig has an auditor, the auditor's clear is the last step, also for a gain above the audit trigger or a change with declared flaws; its block stops the change and says why. A rig with no auditor skips the audit and records it (`audit_skipped`); its supervisor tells the harness which advisors it has. An audit the auditor fails to answer five times goes to the owner with the error; each audit counts its own tries, so a new audit of the same change starts afresh, and a hand-off that does not reach the harness is sent again every 30 minutes until it does. A review panel's pass meets its goal, and a "not possible" proposal ends its goal campaign. **Ask me first about**, on the New campaign page and in Start a run (`ask_owner` over REST, MCP and in `assign_campaign`; `--ask` on the command line), makes a gain above a percent, declared flaws, reviews or "not possible" endings wait for the owner; all are off by default. A run that asked for the owner's approval of every change keeps it. **Needs you** no longer lists an audit that the rig's auditor will decide.
- A goal checked by a kit verifier keeps, as each measured case's values, the numbers the kit's check printed (a ratio, both sides of a comparison, a count), not only the kit's metrics. A kit whose cases check different things can't declare those as metrics, so its met goals kept no numbers before. A held-out case still keeps none.
- A research run's **Research questions** block names each question beside its count of verified claims. Before, its bars had no words: control read the questions' words under a name the rig never sent. It also says what the bars measure, and what the numbers with no source are.

### Operate

- The dashboard says how a run ended. A closed goal run that met its goals reads **Completed**; any other closed run reads **Finished**. With no run at work, a campaign shows its newest run's state, so a campaign whose newest run completed reads **Completed** even with an older run paused. The Campaigns list counts such a campaign as finished, which the default filter hides, and counts its runs as "N completed" apart from "N finished". `get_run` and a rig's view give `goals_complete`.
- A judge-only run, started with its agents off, says so: `judge only` after its mode under its name, a box on its page (`Judge only: No workers run. …`), the mark **judge only** on its cards and under **Earlier runs**, and, while experiments wait in its queue, a line on its **Experiments** tab: no worker takes them, and its **Start a run** link opens the campaign's Start a run panel with that run chosen under **Copy the untried experiments of**.
- A run's goals show their whole text: a long goal, or the judge's long reason, shows its start and **more** opens the rest.
- A decision you make leaves **Needs you** at once, with its count; the change's own page still says what you chose and what the rig did. It comes back only if the rig refuses it or the item needs you again.
- A dashboard button that sends something to a rig says at once that the click took, then follows it to its outcome, with no refresh. The button turns into **Sending…**, a line says `Sent to rig-1 at 03:41 UTC. Waiting for the rig to take it.`, then that the rig took it, then `Done.`, and the parts of the page that it changes are drawn again. A refusal or an expired command says why, and the button comes back. A rig check's row goes from **sent** to **running** with the time so far, such as `running · 1 m 12 s`, and what the check pauses, to its result in place. This covers every command's button (**Run it**, **Check**, **Pause**, **Resume**, **Restart the lanes**, **Export now**, the decisions, the experiment queue and the rules), a message to the agents, **Use** on Providers, **Update to** a version, **Update to these images** and the other buttons of a rig that control set up, **Save changes** on **Edit rig**, and **Start a run**, whose page opens the run's own page once the rig reports it. Without the page's script, each form posts as before, and the page it lands on says `Sent`.
- Model usage. Code records each model call of the workers, the planner and the advisors, never an agent, as a `model_call` event of its run: its tokens in (cached and not cached), its tokens out with the reasoning, and its times, as far as Pi, OpenCode v2, Codex and Claude Code report them. A figure a program does not report is null, never 0. Control sums the records for a run, a campaign (all its runs on every rig) or the whole system, today, over 7 days or for all time, with output tokens a second (median, 10th and 90th percentile) and the cost: each call's tokens at its model's price (the provider's list's, as OpenRouter and Nous Portal give one, else one the owner sets with `POST /v1/model-prices` or the MCP tool `set_model_price`), "on a plan" for a subscription's calls, "no price" where none is known, and a RunPod rig's pod spend for the run it ran: `GET /v1/usage` and the MCP tool `model_usage`.
- Model use on the screens: a run's page shows one line (trials, rounds, its time, its time in calls) and two cards (cost; tokens in, out and tok/s) above its tabs, and its new Stats tab shows its calls in each round and the table by agent and model; a campaign's page shows its model use in its sidebar, with each run; the new Metrics page shows the whole system's, by model and by campaign, for today (in the viewer's time zone), 7 days or all; Settings › Providers has one Model prices table under the providers, which takes your price for each model (In, Cached in, Out, in $ for a million tokens) and shows the provider's own. `GET /v1/usage` and `model_usage` take `tz`.
- Control's log pages through every entry, in the dashboard, over REST and in the `control_log` MCP tool.
- The judge's smoke check passes on a machine with noisy timing when the only wrong result is the no-op's `inconclusive` in place of `neutral`. It then says so in a note: the timing on this machine is noisy, and results there need more repeats. Any other wrong result still fails it.
- The CUDA smoke check works on newer GPUs. Its kit builds native code for every GPU generation from Pascal to Hopper (`sm_60` to `sm_90`), with PTX for newer ones, so no run compiles the kernel when it starts. Each case does five times the work, and its known win is register tiling, several times faster than the naive kernel. Before, on an Ampere card, starting the process took most of each run, and the known win of shared-memory tiling came out at 8%, under the contract's 10%.
- The documentation site has tutorials, how-to guides, reference and explanation. Agents read it through `llms.txt`. It includes the known limits and the security model.
- `CREDITS.md`, also the documentation site's Credits page: the research, systems, programs, libraries, standards and services Thermite draws on, runs or ships, each with its licence.
- `SECURITY.md`, `CONTRIBUTING.md` and a code of conduct (the Contributor Covenant 2.1). CI runs on every push to the development branch: the checks, the docs site, a secret scan, the compose smoke test, the rig image, RunPod against a fake API, and the quick start from the release bundle.

### Removed

- The outside knowledge base: its copies of campaign folders, the advisors' search grant and `THERMITE_OUTSIDE_KB_SYNC_SECONDS`. At the update, each one becomes an MCP server with its token, and a kit names it.
- The old `QWEN_*` names of the model settings, the `thermite-qwen` provider ID and the `qwen-api-key` file migration. Use the `THERMITE_MODEL_*` settings.
- The Kubernetes namespace default `ar-{rig}`. It is now `thermite-{rig}`; a rig with a namespace set keeps it.
